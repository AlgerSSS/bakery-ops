> 图源：[HOTCRUSH未来数据库蓝图.drawio](HOTCRUSH未来数据库蓝图.drawio)

## 一、这张图解决什么问题

老板提出的不是“再加一张预估单”或“把班表放进 BakeryOps”这么简单，而是要形成一条可追溯的经营事实链：

1. 明天预计卖什么、计划做多少；
2. 计划改变了什么、为什么改变；
3. 需要多少原料、未来订货增减多少；
4. 实际发出、实际售出、报废分别是多少；
5. 原料采购价和配方变化后，当日产品成本与毛利是多少；
6. 当天需要什么岗位、谁具备资格、谁被排到关键岗位；
7. 实际工时与销售结果结合后，人效是多少。

这些问题不能靠一张“大宽表”可靠回答，因为预估、计划、发出、销售、采购、班表和工时的业务粒度不同。正确路径是：**一个 BakeryOps 工作流可以一次提交多个动作，但数据库在同一事务中分别写入正确粒度的表，再用稳定 ID 串联。**

## 二、六条不可妥协的建模原则

### 1. 稳定身份先于跨表分析

所有跨域连接只使用：

- `store_id`：企业门店；
- `product_id`：企业可售产品；
- `employment_id`：一段有效雇佣关系；
- `material_id`：标准原料。

外部系统的名称、商品 listing、员工姓名、供应商 SKU 都只作为“来源身份”。名称不一致时进入映射审核队列，不能静默猜配。

### 2. 一表一个事实粒度

- 预测运行不等于已发布计划；
- 已发布计划不等于实际发出；
- 实际发出不等于实际生产；
- 实际生产不等于 POS 售出；
- POS 售出不等于报废；
- 计划班表不等于 Lark 实际工时。

空白也不等于 `0`。空白表示“不知道/未录入”，`0` 表示已确认没有发生。

### 3. 版本不可覆盖

预估单、采购单、配方、原料价格都必须保留版本、生效时间、原因、审批人与来源。历史毛利必须使用交易日当时有效的配方和价格，不能用今天的成本倒算过去。

### 4. 自动采集事实，人工录入判断

POS 销售、报废、官方节假日、Lark 实际工时、成本汇总、产品占比、预测误差和毛利全部自动产生。人工只确认系统无法判断的业务动作和证据。

### 5. 一张表只有一个写者

- `res_api` 写 `pos_`；
- BakeryOps 写 `ops_`、`hr_`、`scm_`；
- 财务网站写 `finance_`、`cost_card_`、`app_`。

BakeryOps 可以读取成本卡并发起业务流程，但不能绕过成本卡所有者直接改写成本事实。

### 6. 核心事实先建，视图和 mart 后置

毛利、人效、预测准确率、补货状态都是核心事实的投影。上游身份、粒度或版本错误，不能靠下游宽表修复。

## 三、老板建议如何落到数据库

| 老板建议 | 结构化答案 | 主要目标表 |
|---|---|---|
| 跨表抓取、同时录入更快 | BakeryOps 一次提交，在一个事务里分别写父表、版本表和明细表 | `ops_production_plan*`、`ops_shift_plan*`、`ops_plan_adjustment` |
| BakeryOps 加入门店预估单 | 建“门店×日期”的计划身份，版本与产品明细不可覆盖 | `ops_production_plan`、`_version`、`_line`、`_slot` |
| 明日计划调整动作 | 调整是独立业务动作，保存增减量、原因、提交人和审批状态，再生成新版本 | `ops_plan_adjustment` |
| 当日突发情况 | 事件有时间范围、门店、类型和证据；受影响产品另建明细 | `ops_operational_event`、`_product` |
| 节假日 API 网上抓 | 官方日历事件与事后观测到的销售影响分开 | `ops_calendar_import_batch`、`ops_calendar_event`、`ops_demand_factor_observation` |
| 预估单连接供应链 | 只用已发布计划 × 生效配方版本计算原料需求 | `scm_material_requirement_run`、`_line` |
| 未来订货量增减 | 系统建议量与人工批准量并存；每次改动保存采购单版本 | `scm_replenishment_run`、`_line`、`scm_purchase_order_revision` |
| 采购价按市场波动 | 每次到货实价成为带来源的价格候选，批准后形成有效期价格版本 | `scm_goods_receipt_line`、`cost_card_item_price` |
| 成本按配方波动 | 配方和原料价格均版本化，再锁定产品日成本快照 | `cost_card_recipe_version*`、`cost_card_product_cost_snapshot` |
| 产品占比上涨或下降 | 以 `store_id + date + product_id` 自动计算销量占比和环比 | `v_ops_product_mix_daily` |
| 成本卡和销售联动当日毛利率 | POS 收入连接当日有效成本快照，不用当前成本回算历史 | `v_ops_daily_product_margin` |
| 人事打分到入职培训到细节班表 | 评分、雇佣、培训结果、岗位资格、班表需求和人员指派分层连接 | `hr_assessment*`、`hr_employment`、`hr_training_*`、`ops_shift_*` |
| 值班关键岗位必须写明 | 班表需求写 `is_critical`；发布前校验岗位已指派且员工有资格 | `ops_shift_requirement`、`v_hr_role_eligibility` |
| 人事事实和班表连接 | 班表指向稳定 `employment_id`；实际工时从 Lark 单独同步 | `ops_shift_assignment`、`hr_timesheet_entry` |

## 四、预估单和班表：人工到底录什么

### 自动采集或自动计算

- POS 销售、单品销量、报废、交易时段；
- 官方节假日和政府日历；
- Lark 每日实际工时；
- 预测结果、产品销量占比、预测误差；
- 原料需求、在途、订货建议；
- 产品成本、毛利额、毛利率和人效。

### 一次性人工确认

- 门店来源标识 → `store_id`；
- POS 商品/listing → `product_id`；
- `product_id` → 成本卡成品；
- 供应商 SKU → `material_id`；
- Lark/招聘人员 → `person_id` / `employment_id`。

### 日常人工判断

- 明日计划覆盖量、增减量和原因；
- 当日突发事件和受影响产品；
- 无自动来源时的实际发出量；
- 面试/试岗评分和证据；
- 培训结果；
- 班表调整与关键岗位指派；
- 系统建议订货量的批准值和原因；
- 无 WMS 时的收货确认或收货异常。

### 绝不人工重复录

销售额、总工时、产品占比、原料需求合计、成本合计、毛利率和人效。这些数据已有事实来源或可以确定性计算，重复人工录入只会制造冲突。

## 五、三条端到端事实链

### 营运

`官方日历 + 历史销售 + 当日事件`  
→ `ops_forecast_run / line`  
→ `ops_production_plan / version / line / slot`  
→ `ops_dispatch / line`  
→ `POS 销售 + 报废`  
→ `计划偏差、产品占比、预测准确率`。

### 供应链与成本

`已发布计划行`  
→ `product_id → 成本卡成品 → 生效配方版本`  
→ `原料需求`  
→ `库存 + 在途 + 安全库存`  
→ `补货建议 → 采购单版本 → 收货实价`  
→ `原料价格版本 → 产品日成本快照`  
→ `POS 销售 → 当日产品毛利`。

### 人事与班表

`候选人评估`  
→ `人员与雇佣关系`  
→ `培训安排和结果`  
→ `岗位资格`  
→ `班表岗位需求 + 人员指派`  
→ `关键岗位发布门禁`  
→ `Lark 实际工时 + POS 销售`  
→ `门店/工作区域人效`。

## 六、黑巧和草莓塔作为验收样本

“黑巧”和“草莓塔”不应成为数据库里的特殊列或硬编码名称，而应成为首批端到端验收用例。每一款产品必须能从同一个 `product_id` 追到：

1. POS 来源 listing；
2. 预测与已发布计划；
3. 配方版本和所有原料；
4. 补货建议、采购单版本和收货实价；
5. 实际发出、售出和报废；
6. 当日单位成本、毛利额与毛利率。

如果名称漂移、疑似错配或一对多不明确，记录进入映射审核队列并阻断下游计算；不能为了“跑出数字”而自动猜配。

## 七、当前库为什么不能直接在上面继续堆表单

本次只读审核确认了几项结构性问题：

- 单品销售事实缺少可靠门店键，部分行缺少商品映射键；
- 现有预测快照按日期和名称覆盖，缺少运行、版本、门店和稳定 `product_id`；
- 现有班次事实为空，且计划班表与实际工时边界不清；
- 成本价格没有足够的生效历史，历史毛利存在使用当前成本回算的风险；
- 供应商商品名称与成本卡名称只有少量精确匹配，不能用名称直接 join；
- 招聘数据已有申请，但试岗、offer、培训和班表闭环尚未形成；
- 节假日身份与节假日实际销售影响被混在同一层；
- 共享生产库的迁移版本、校验和与写者登记需要先治理。

因此最短路径不是先做一张“预估单+班表+订货”大表，而是先补共享身份和版本事实，再把 BakeryOps 表单接上这些结构。

## 八、推荐实施顺序

1. **迁移治理**：确认每张表的所有读写者；修复 `schema_migrations` 的版本、checksum、owner 和串行锁。
2. **共享身份**：建立门店、产品、雇佣关系、原料及来源映射；先跑映射审核队列。
3. **营运核心**：落地预测运行、预估单版本、调整动作、实际发出和经营事件。
4. **人事核心**：落地评分、培训、岗位资格、班表需求/指派和 Lark 实际工时同步。
5. **供应链核心**：落地原料需求、库存、补货建议、采购单版本和收货事实。
6. **成本历史**：版本化配方与原料价格，生成产品日成本快照。
7. **分析视图**：最后建立毛利、人效、预测准确率、产品占比和补货状态。
8. **并行验收**：用黑巧和草莓塔跑完整链路，至少并行一个业务周期后再停用旧表单。

本蓝图没有执行数据库 DDL/DML，也没有修改或部署任何上层应用。
