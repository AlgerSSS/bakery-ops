## 一、先说结论:他要的东西全部卡在同一个点上

**近 30 天在卖 67 个商品,净销 RM 1,502,687。能算出成本的:0 个,RM 0,覆盖率 0.0%。**

不是成本卡不行 —— 成本卡本身很健康:`v_cost_card_current_cost` 能算出 **270 个**商品的成本,只有 14 个缺价。

断点在一张 94 行的映射表:

```
cost_card_product_link.external_source  →  全部是 'mysql:v_product_direct'
cost_card_product_link.external_key     →  MySQL 那边的键
item_hourly_sales.item_key              →  Restosuite POS 的键
                                            ↑ 两者匹配 0 条
```

> **这 94 行指向的是一个已经不在链路里的 MySQL 系统。**

他提的每一件事都过这个点:
- 「成本卡和销售联动当日毛利率」→ 差这张表
- 「预估单连接供应链、销售运营事实、和成本卡串起来,product-id」→ 差这张表
- 「未来订的货量增减」→ 预估单 × BOM 展开才能算订货量,差这张表
- 「某个产品占比上涨或者下降 → 和成本卡相关」→ 差这张表

**所以第一件事不是建新表,是把 `cost_card_product_link` 从 MySQL 键改挂到 `item_key`。**
成本卡侧 99 个 product 类物料,POS 侧 65 个有 `item_key` 的在卖商品 —— 是一次可以做完的人工对表。

## 三、成本卡的视图为什么看着乱 —— 有实证

9 个视图,**4 个运行时零引用**:

| 视图 | 列数 | 运行时引用 | 判定 |
|---|---|---|---|
| `v_cost_card_current_cost` | 核心 | **3** | ✅ 主力,270 个商品的成本从这里出 |
| `v_cost_card_data_quality` | 6 | **3** | ✅ 在用。当前告警:缺售价 232、缺采购价 14 |
| `v_cost_card_price_current_normalized` | 13 | **2** | ✅ 在用(单位/汇率归一) |
| `product_material_cost` | 5 | **2** | ✅ 在用 |
| `v_cost_card_price_current` | 7 | 1 | ⚠️ 它是 `_normalized` 13 列的**子集**,两个并存 |
| `v_cost_card_recipe_expanded` | — | 0 | ⭕ 中间层,被 `current_cost` 内部依赖,合理 |
| `v_cost_card_product_material_cost_compat` | 5 | **0** | ⚠️ 纯转发层 |
| `v_cost_card_product_cost_compat` | 5 | **0** | ❌ |
| `product_cost` | 5 | **0** | ❌ |

**乱在三处:**

**① `product_cost` 整条链是死的。**
```sql
product_cost = SELECT ... FROM v_cost_card_product_cost_compat;   -- 纯别名,123 字符
v_cost_card_product_cost_compat = ... '供应链单位成本（非月度消耗）'::text AS project_name ...
```
两个视图对象,零消费者。那个硬编码的中文标签暴露了它的来历 —— 为兼容某个旧调用方造的,而调用方已经没了。

**② `product_material_cost` 中间多一层纯转发。**
`product_material_cost` → `..._compat` → `current_cost`。中间那层可以直接拿掉,改成一层。

**③ 命名三套并存。** 有 `v_` 前缀的、没前缀的、带 `_compat` 的,同一个东西三种叫法。

**建议:9 个视图收敛到 5 个** —— 删 `product_cost` + `v_cost_card_product_cost_compat`(零引用),把 `product_material_cost` 直接建在 `current_cost` 上(去掉中间层),`v_cost_card_price_current` 与 `_normalized` 二选一。

> **但注意:成本卡的建模思路本身是全库最好的一块** —— 成本一行都不落表,全部现算,改配方或改价立刻反映。乱的是外层那几个为已消失的系统留的兼容壳,不是核心。清完就干净了。

## 四、「跨表抓取」还是「bakery-ops 加门店预估单」

**答案是后者,但理由不是「更快」。**

跨表抓取(同时录入多张表)的问题不在性能,在**一次录入产生多个事实,失败时不知道哪个成功了**。而这个库现在恰恰没有跨表事务的纪律 —— 财务站为此造了一整套幂等账本,而 100% 的数据是从没上锁的另一扇门进来的。

正确的做法是:**bakery-ops 内建预估单,一次录入只写一张事实表,其余全部由视图现算。**

```
门店录预估单(计划量)
      ↓  一次写入，一张表
 fact_production_plan(生产日, 门店, item_key, 版本, 计划量)
      ↓  ↓  ↓   全部现算，不再录入
      ↓  ↓  └→ × BOM 展开  → 物料需求量 → 订货建议
      ↓  └───→ × 成本卡     → 计划成本 → 与售价比 → 计划毛利率
      └──────→ vs 实际销售  → 产销率 / 预测偏差
```

这正是「用最小的数据存最多的信息」:**录一次计划量,推出订货、成本、毛利、产销率四件事。**

前提还是第一节那张映射表 —— 没有它,这三条箭头一条都拉不通。

## 五、人工录入什么(他专门问的)

分工线画在**「机器知道的」和「只有人知道的」**之间:

| | 来源 | 谁录 |
|---|---|---|
| 昨日销量、时段分布、报废 | POS 自动 | 机器 |
| 建议产量 | 算法(现有 `forecast_snapshot`) | 机器 |
| **实际排多少** | 店长看了建议之后的决定 | **人** |
| **为什么调整** | 「明天有市集」「昨天剩太多」 | **人**(枚举 + 备注) |
| 节假日、系数 | API 抓 + `holiday.coefficient` | 机器,人可覆盖 |
| **当日突发** | 停电、设备坏、临时团单 | **人** |
| 物料标准用量 | BOM(`cost_card_recipe_item` 1,527 行) | 机器 |
| 采购价 | 供应商报价 | **人**(但必须版本化,见下) |
| **谁上什么班、什么岗** | 排班 | **人** |
| 实际工时 | 打卡 | 机器(现在没有) |

**人只录三类:决定(排多少)、原因(为什么调)、事实(谁上班、报了什么价)。其余全推。**

## 六、建议的顺序 —— 他说「先梳理再摘数据」,这个顺序对

```
第 1 步  修 cost_card_product_link:94 行从 MySQL 键改挂 item_key
         ← 他要的每一件事都卡在这里。做完当日毛利率立刻能算
第 2 步  cost_card_item_price 改成版本化(加 effective_from/to,不再覆盖)
         ← 现在每物料 1 行,改价即丢历史,「采购价随市场波动」无从谈起
第 3 步  forecast_snapshot → fact_production_plan
         加 item_key、门店、版本、调整原因、备注。旧表保留只读
第 4 步  建 fact_shift(排班):日 × 门店 × 员工 × 岗位 × 班次
         「值班关键岗位」进主键,人事事实由此连上
第 5 步  节假日改 API 抓,保留 coefficient 人工覆盖
第 6 步  订货建议视图:fact_production_plan × BOM → 物料需求
         ← 到这一步「未来订货量增减」才是推出来的,不是又一张录入表
第 7 步  成本卡视图收敛 9 → 5
```

前两步做完,「成本卡和销售联动当日毛利率」就成立了。
第 3、4 步做完,预估单和班表才谈得上「串起来」。
**第 6 步是收成 —— 但它必须排在最后,因为它是纯推导,前面任何一环没通它就是空的。**

## 七、要跟领导确认的三件事

1. **`cost_card_product_link` 那 94 行的 MySQL 来源还在不在?** 如果那个系统还在跑,改挂 `item_key` 之前要先弄清它是不是另一条在用的链路。
2. **订货是一张表还是两张?** 现在 `finance_orders`(月度台账,财务站所有)与将来的「日订货建议」粒度不同、所有者不同。合并还是并存,是他的决定。
3. **排班的粒度到哪一层?** 「值班关键岗位必须写明」—— 是「岗位」还是「岗位 + 时段」?这决定 `fact_shift` 的主键,建完再改代价大。
